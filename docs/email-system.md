# CRM email receiving and replies

## Received images and file compatibility

The reader resolves CID and Content-Location image references, including Foxmail BMP icons sent as `application/octet-stream`. Authenticated attachment responses detect raster formats from their original bytes. PNG, JPEG, GIF, WebP, BMP, AVIF, ICO and PDF can display in the browser; other formats remain downloadable. Unsupported active documents such as HTML and SVG download instead of executing on the CRM origin. MIME-encoded and continued international filenames decode correctly, and binary images with unusable extensions receive the detected extension on download. GIF and other original file bytes are not converted.

Shared CRM reply rows retain their CRM identity but can load the exact original HTML and files through `/api/email/crm-message` and `/api/email/crm-attachment`. Each request verifies current CRM contact visibility, derives the source account from the saved row's owner, and matches both original Message-ID and sender. Requests cannot choose a private mailbox/UID; only attachment part IDs listed on that exact message are downloadable. Private source locators are not returned to the browser. Attachment checks read metadata without transferring the full HTML body. Replies not associated with an available original retain their stored text; missing source images are identified rather than silently discarded.

Plain-text `[cid:...]` markers recover matching embedded images, and legacy body caches can recover original HTML on opening. Background inbox refresh retains loaded attachment and recipient metadata while preserving current provider flags. Embedded files have their own expandable download list, including images that a browser cannot preview. Copying and forwarding BMP, AVIF and ICO images uses CID attachments, alongside the existing PNG/JPEG/GIF/WebP support.

The composer accepts general file attachments, including archives, presentations, CAD files, audio/video and files with an empty browser MIME type. The existing 7.5 MB per-file and ten combined images/files limits remain. This does not imply every file format has an in-browser preview. Verification includes MIME/filename fixtures, forwarded `.eml` bytes, CRM access-denial tests and a receive-only check of the reported Foxmail email. Browser evidence is `docs/audit-evidence/email-cid-signature-20261030.png`; all 16 embedded images loaded with decoded dimensions.

## Durable receive worker

Mailbox refresh persists deduplicated work in `mail_sync_jobs`; it never starts IMAP through Next `after()`. The independent `/api/cron/mail-sync` worker drains this queue with account-wide database leases, renewal, expiring ownership and fenced snapshot commits. Separate jobs handle new Inbox headers, other folders, older history, previews, flags/removals and folder discovery. Each successful batch commits separately. Transient failures retain saved mail and checkpoints, and retry with exponential backoff and jitter. Automation readers consume the saved Inbox rather than initiating competing background imports. On-demand message/attachment downloads and explicit user mutations still contact the provider.

The existing Supabase scheduler invokes this receive-only endpoint once a minute with the existing vault cron origin and secret. Its Node runtime is bounded to 300 seconds; each job leaves time for the provider's existing connection/operation timeout. Two independent accounts may progress concurrently, while all jobs for one account share a lease. A terminated invocation is recovered after the five-minute account lease expires. The UI shows per-folder last successful checks, delayed mail, automatic retries, sign-in failures and history progress; failures in Trash/history do not become an Inbox error. This is scheduled polling, so a 30-second recurring-job interval is not a 30-second delivery guarantee. No persistent external host is required.

For a persistent Node host, `npm run mail:worker` runs the same receive-only queue continuously; append `-- --once` for one tick. It needs the existing server Supabase environment in `.env.local`. It does not send mail or execute contact follow-up actions. Continuous operation can coexist safely with the scheduled worker, but is optional.

## Conversation AI auto-reply

Open a received email, expand Reply, then open **AI tools → AI auto-reply**. The menu contains a compact On/Off switch; policies are available from its book icon. Every conversation starts off. Status reads query the saved setting directly. Enabling records the activation time and latest saved incoming header without waiting for provider sync, message downloads, or AI generation. Requests have a timeout and retry control, and initial loading also works in background app views. It does not answer historical mail. Only future RFC-linked replies in that mailbox are eligible. Automatic replies use the receiving mailbox so customer replies keep arriving in the monitored account. Other conversations retain their own opt-in state. The setting is not shown in the inbox list.

The worker loads original saved conversation bodies and current database products, prices, customer billing/delivery details, invoice defaults, and approved business facts. Unsupported policy questions, human requests, ambiguous orders, unavailable context, automatic messages, and delivery failures create a review handoff instead of sending an unsupported answer. Catalog requests generate a personalized PDF before sending. Matched CRM customers reuse their saved catalog selection unless the request calls for a specific product subset; new selections are saved in their catalog history. Unknown correspondents can receive a personalized PDF without automatically creating a CRM company.

For an invoice request with exact items and complete billing and delivery details, the worker sends no reply. ## Current flow

1. `/emails` and `/api/email/inbox` return saved messages immediately. Ordinary browser polls only read saved results; manual refresh expedites the durable queue. The browser checks every 10 seconds while visible, and on focus.
2. The account-wide database lease permits one provider operation per mailbox across server instances. `mailbox_sync_state` records UIDVALIDITY, the last acknowledged UID, errors, and up to 5,000 recent headers per folder. A failed sync preserves the previous snapshot and cursor. Expired leases are reclaimable, and fenced commits reject an expired worker.
3. New-mail sync imports up to 100 headers per batch, oldest first after the checkpoint. Initial sync takes the latest 100. History continues automatically in batches of 200, reducing to 50 and 25 after timeouts, without rewinding the new-mail checkpoint. A UIDVALIDITY change discards the old epoch's cache and restarts history. History jobs stop at completion or the 5,000-header retention cap.
4. Opening a message calls `/api/email/message`. Only that message's plain-text and HTML MIME parts are downloaded, decoded with MailParser, and saved in `mailbox_message_content`. Older messages in a conversation have a Load message control. Attachments download separately through an authenticated route; inline image CIDs resolve through the same route, matching complete and URI-encoded IDs. The HTML viewer allows same-origin attachment cookies while keeping scripts, forms, and top-level navigation blocked. PNG/JPEG images and animated GIFs use the original attachment bytes.
5. The receive-only background worker uses ImapFlow with bounded connections and commands, handles unsolicited mailbox events, and reuses connections within each tick. It closes only its own connections on exit. Header commits happen before separate preview and flag jobs, so large bodies and attachments cannot block new mail. Text previews fetch at most 16 KB per message; full bodies and files load on demand. Foreground message/file operations retain their separate sessions.
6. The `filazoo-mail-sync` database schedule is configured for every 10 seconds. The authenticated endpoint acknowledges with HTTP 202 immediately and runs the receive worker using Next.js `after`, keeping pg_net's shared HTTP batch free. A reserved server-only `mailbox_sync_state` row leases one warm cron worker for five minutes; competing ticks return immediately, expired owners are reclaimable, and release checks its token. The worker polls for available work for up to 225 seconds before its final operation, leaving execution headroom, with up to four accounts in parallel. Account-wide leases also protect each provider operation. Inbox jobs run first and become eligible again after 15 seconds; history precedes optional preview and flag maintenance. Transient failures retry with backoff. Fresh installations leave the schedule inactive until the matching application release is live. Existing automation reads the saved cache and does not compete for provider synchronization.
7. The inbox shows one compact sync status and optional history progress. Routine queued work is neutral; delayed, retrying, or invalid-credential states remain visible. Successful history completion removes the older-mail import control until explicitly requested again.

## Conversation and sending rules

- Threading follows Message-ID, In-Reply-To, References, and saved CRM keys, including incomplete immediate-parent chains. Identical subjects alone do not combine inbound conversations. The restricted legacy outbound `Re:` fallback remains for older sent records.
- IMAP and CRM copies of the same received Message-ID are deduplicated. Saved CRM replies retain their message and thread identifiers.
- Reply uses the latest inbound Reply-To, or its From address. Sent-only conversations continue to the sent recipient. The composer displays the actual destination and keeps new-email composition separate.
- Reply headers retain original message-ID casing. Normal new messages have no reply headers. Plain text is not passed as HTML; explicitly supplied HTML remains a separate MIME alternative. SMTP connections have bounded timeouts and close after sending.
- Recognized quoted history is collapsed in the reader, with the original complete message available to expand.

Both cache tables have RLS enabled and deny direct anon/authenticated access. Server routes resolve the viewer's authorized effective mailbox and check its opaque mailbox key before serving content or attachments. Credentials are never stored in the cache or printed by the verification script.

The inbox cache intentionally retains at most 5,000 headers per provider folder; it is not a complete mailbox archive. Attachments are downloaded only on demand and capped at 25 MB per MIME part. Full external delivery and provider spam placement were not tested by sending customer email: MIME sending checks use Nodemailer's local stream transport.

The database migration is `supabase/migrations/20261022055049_mailbox_incremental_sync.sql`; equivalent table definitions are in `supabase/schema.sql`. Application changes require deployment to affect the hosted CRM.

## BD manager email visibility

For workspace mailboxes, the email page and inbox API restrict BD managers to saved contact addresses on companies currently assigned to them through `pipeline.owner_id`. This includes automatic and manual assignments and every contact on each company. Other managers' customers, unassigned customers, and unknown senders are excluded from every workspace inbox folder and its automation queue count. Matching uses exact email addresses, never company names or domains. Workspace message bodies and attachment downloads enforce the same assignment check. Assignment lookup errors deny workspace access; they do not fall back to the shared inbox. Personal mailbox owners can view every synced sender, message body, and attachment regardless of CRM assignments; other users cannot access that personal mailbox. Sent attachments resolve the message's stored mailbox ID rather than inferring ownership from the current default sender. Admin, operator, and viewer workspace access is unchanged.
