# CRM email receiving and replies

## Inline images in email drafts

New emails and replies, including the company Email tab, accept pasted PNG, JPEG, WebP, and GIF images at the current cursor position. Clipboard HTML supports images, links, tables, and basic text formatting; active content and unsupported URL schemes are removed before insertion. Copied web images are imported before insertion so accessible GIFs retain their original animation instead of using a static PNG snapshot. Saved personal footers appear inside the editor and can be edited or have images pasted between their lines for that message. There are no extra image controls or helper rows; the original reply toolbar remains at the bottom.

Local pasted images become CID MIME attachments without resizing or re-encoding, preserving GIF animation. Each image can be at most 7.5 MB; messages support ten images and file attachments combined. Image-only emails are supported. Automatic AI writing is bypassed for images in the message body to retain their layout; saved footer images remain compatible with AI writing. Existing catalogs, invoices, sender selection, and manual Send behavior remain in place. Collapsing a reply retains its images, and browser undo/redo supports paste operations.

Sent history retains the original HTML separately from plain text in `mailbox_sent_messages.body_html`, with CID values in existing private attachment metadata. Both the send response and subsequent inbox reads resolve CIDs to the authenticated attachment endpoint, which serves PNG/JPEG/WebP/GIF with their original MIME types and bytes. The additive migration is `supabase/migrations/20261029080121_email_inline_images.sql`, applied to the linked Filazoo project on October 29, 2026. Existing ownership and customer-assignment checks still apply.

Verification covers native clipboard image paste, signature GIF placement, undo/redo, collapse/reopen persistence, toolbar spacing, and local MIME encoding/decoding with a two-frame animated GIF. No test email is sent to a customer. Application changes require deployment before they appear on the hosted CRM.

## Personal custom email footers

**Settings → Email preferences → Custom email footer** replaces the plain-text signature form with a rich editor, image/GIF upload, link insertion, formatting controls, icon picker, and preview. Each account saves its own footer. Empty saved footers disable automatic inclusion; existing text signatures are migrated without changing their content. Footer media is stored privately outside Auth metadata, so images never enlarge session cookies.

Inbox drafts and company replies show the footer while writing. AI rewrites retain the current footer, including message-specific edits. Direct AI-agent sends, invoice emails, customer-information requests, conversation auto-replies, flow emails, and flow delivery tests use the initiating user or automation owner's footer. The server appends it once, replaces generated standard sign-offs, embeds original image/GIF bytes as CID attachments, and saves the resulting HTML and image metadata in Sent mail. Existing permissions, reply headers, send approvals and dry-run rules remain in force.

Full-signature paste preserves basic font styles, table layout, links, emoji, image dimensions, and cursor placement. External images are copied through an authenticated importer that validates public destinations and redirects, bounds downloads, and verifies raster formats. Private network destinations are rejected. A webmail image locked behind its original login can use a clipboard image file when one is provided; otherwise the surrounding signature text is retained and the editor asks for the original image file. Images are never silently saved as broken remote references. HTML indentation stays whitespace rather than becoming extra blank lines. Footer media totals are limited to 5 MB, with up to ten images.

Copies from the CRM email reader use authenticated attachment downloads directly, including a signature copied from the hosted CRM into the local editor. Received-attachment, sent-attachment and footer-asset URLs retain the current viewer's existing ownership and assignment checks; they are never sent to the public image importer. Browser verification with the reported **Fw: RE: PETG-CF Filazoo** signature loaded all seven images (including its original animated GIF and five icons) with no image errors. The preview uses the editor's text defaults and expands to the footer height rather than adding a nested scrollbar for normal signatures.

The additive `20261029082104_personal_email_footers.sql` migration creates server-only `email_footers` with RLS and revoked browser-role access, and migrates prior text signatures. It was applied to the linked project on October 29, 2026. Rollback-only database verification checks saving and reading without retaining test settings; ownership, sanitization, GIF byte preservation, sign-off replacement, footer removal, failed-save cleanup and remote-import restrictions are covered in `tests/email-footers.test.ts`. Browser verification uses unsaved test signatures and sends no email.

## Flow AI auto-reply

The **AI auto-reply** flow step always writes customer emails in English, including greetings, sign-offs and generated subjects. Existing `auto` and `zh-CN` settings also use English; saving a flow normalizes these legacy values. Chinese prose in a generated draft triggers one regeneration, then blocks delivery if it persists. Supplied customer and product names remain unchanged. A Chinese inbound subject uses the generated English subject while retaining reply-thread headers.

When catalog attachments are enabled, a separate AI planning step selects the scope before the email is drafted. The first automated email includes a catalog when **Also include catalog in the first email** is on. Later emails attach one only for a customer request or a clear product-discovery need. Declined catalogs and fulfilled requests are respected. Disabling the first-email option does not force catalogs onto follow-ups. The existing `catalogFirstMessageOnly` field now controls this first-email inclusion; it does not prevent later requested catalogs.

Specific material or product requests limit the PDF to selected active CRM SKUs, including on the first email. A PLA request must select only matching PLA products. General requests can receive the full range. Unknown or ambiguous requirements require clarification without falling back to the full catalog; invalid or empty specific SKU selections block generation. The reply prompt receives the actual attachment selection before drafting. Product selection remains an AI decision, with exact SKU availability checked by the server. Catalog planning and drafting use the existing provider and regional fallback; no new catalog is saved to company history by a flow reply.

## Conversation AI auto-reply

Open a received email, expand Reply, then open **AI tools → AI auto-reply**. The menu contains a compact On/Off switch; policies are available from its book icon. Every conversation starts off. Status reads query the saved setting directly. Enabling records the activation time and latest saved incoming header without waiting for provider sync, message downloads, or AI generation. Requests have a timeout and retry control, and initial loading also works in background app views. It does not answer historical mail. Only future RFC-linked replies in that mailbox are eligible. Automatic replies use the receiving mailbox so customer replies keep arriving in the monitored account. Other conversations retain their own opt-in state. The setting is not shown in the inbox list.

The worker loads original saved conversation bodies and current database products, prices, customer billing/delivery details, invoice defaults, and approved business facts. Admins and operators manage shared policies inside **Business facts & policies** in the AI tools control. Unsupported policy questions, human requests, ambiguous orders, unavailable context, automatic messages, and delivery failures create a review handoff instead of sending an unsupported answer. Excessive context is handed to a person rather than silently discarding history.

Catalog requests generate a personalized PDF before sending. Matched CRM customers reuse their saved catalog selection unless the request calls for a specific product subset; new selections are saved in their catalog history. Unknown correspondents can receive a personalized PDF without automatically creating a CRM company.

For an invoice request with exact items and complete billing and delivery details, the worker sends no reply. It atomically creates an assigned task and notification, stores the pending document, and waits for shipping confirmation. **Tasks and notifications** shows the items, destination, currency, shipping-cost field, and **Add shipping and send invoice**. The compact AI tools switch shows the handoff status and a **Review task** link. Zero is accepted only as an explicit free-shipping approval. New customer corrections invalidate stale approval. After confirmation, the worker creates the invoice using verified product prices, includes the approved shipping amount, generates its PDF, and sends it in the original thread. Existing billing permissions remain: admins/operators can issue the invoice; BD managers create and send a clearly labeled draft for review.

Turning **AI auto-reply** off disables the conversation and cancels its open handoff task. Sending a manual CRM reply also stops its linked automation. Workers recheck permissions, mailbox status, suppression, daily limits, the latest customer message, and the opt-in revision before SMTP. A transport operation already accepted by SMTP cannot be recalled. Durable per-message reservations prevent automatic delivery retries after ambiguous or interrupted sends; those require review. The existing dry-run setting continues to block live automated sends.

The existing flow cron and inbox-refresh background worker process these settings. Idle shipping tasks rotate behind other due conversations without invalidating their forms. Legacy flow emails defer only when an enabled conversation automation matches the same mailbox and thread. Existing mailbox and task features remain usable before the additive migration is installed.

Database setup: apply `supabase/migrations/20261028065808_conversation_ai_auto_reply.sql`. It adds server-only `email_auto_replies`, `email_auto_reply_deliveries`, `email_reply_knowledge`, and the atomic `handoff_email_auto_reply` RPC. RLS is enabled and browser-role grants are revoked. The migration does not enable any conversations. Applied to the linked Filazoo project on October 28, 2026 after user approval. Rollback-only database checks passed for defaults, permissions, shipping tasks and notifications, stale revisions, duplicate delivery reservations, and manual stops; no conversations were enabled and no customer emails were sent. Verify with `tests/email-auto-reply.test.ts`, `tests/email-auto-reply-route.test.ts`, and the rollback-only `tests/email-auto-reply-database.sql` after migration.

## Personal and workspace accounts

The main Email page has an account tab for each workspace mailbox and each personal mailbox owned by the signed-in user. Selecting a tab loads that account's saved inbox and sent history; refresh and history import target the same account. A personal mailbox shows every synced sender and its saved sent history without requiring a matching CRM customer or assignment. Shared Shopify leads and CRM outreach history remain in the workspace view, where BD customer-assignment restrictions apply. Other users' personal accounts are excluded from these tabs and from message, attachment, and sending access, including for admins.

Both new-email and reply composers have a From selector. They start with the user's default personal mailbox, or their active personal connection if none is marked default, and use the workspace default when no personal connection is available. The sender choice is independent of the mailbox being read. Each send resolves the selected account again on the server, uses its SMTP credentials and From address, and saves its mailbox ID with sent history. Stopped, removed, or unauthorized selections fail without silently switching accounts. A stopped default also requires an explicit sender change. Tabs preserve an unfinished draft by requiring the user to finish or clear it before navigating away.

Account switches use the authenticated inbox API rather than rerendering the whole page and reloading products and catalogs. Authorized alternative accounts preload saved snapshots with `refresh=false`, without starting provider synchronization. Loaded snapshots remain in memory for the current Email page and revalidate when their inbox mounts. Reading or editing mail updates that snapshot, including opened bodies and saved folder/read/star state, instead of deleting the cache. A later response from an abandoned selection can warm its account without changing the selected tab. Unmounting cancels pending preloads. Failed switches retain the current account. Browser history records successful switches. Inbox lists request headers without hydrating the full cached message bodies; opening a message still uses the content endpoint. Personal inboxes skip shared outreach and Shopify queries, and inboxes without visible messages skip company enrichment. Opening an inbox performs an initial refresh even when periodic refresh is disabled.

The inbox route authorizes the viewer and loads authorized mailbox settings once, then passes that server context to the inbox loader and shared outreach reads. Customer enrichment queries only the displayed correspondents and assigned company IDs, including secondary contact addresses. It excludes the global company list, nested outreach history, and Auth/Storage avatar lookups. `Server-Timing` separates authentication from saved-inbox loading. On October 28, a read-only local benchmark loaded the Gmail snapshot and its customer context in 781 ms, and the shared mailbox snapshot and relevant customer context in 2,362 ms. These measure database reads, not full browser response or provider sync time. Preloaded tab switches do not wait for those reads.

The BD workspace view explicitly explains its assigned-customer restriction. On October 28, 2026, a read-only database check found 10 saved messages for the reported Gmail account, none matching its owner's assigned customer contacts. Both saved snapshots had no sync error. The personal inbox was incorrectly empty because it applied workspace customer restrictions. Personal inbox lists, sent history, message content, and received and sent attachments now use personal mailbox ownership without querying customer assignments. The workspace mailbox had 151 saved messages, of which eight matched that owner's contacts, and retains its assigned-customer restriction.

## Company Email tab

Company profiles include an Email tab (`/companies/[id]?tab=email`) using the existing mailbox reader and reply composer. It starts in All mail so incoming messages and saved sent replies appear together. Messages match the company's primary and additional saved contact email addresses exactly, ignoring case and surrounding whitespace; company names and shared domains never expand the match. Companies without an email address show guidance to add one.

Company history combines the viewer's own personal accounts and authorized workspace accounts, independently of the default sending account. Each account retains its existing ownership and customer-assignment checks before company filtering. Duplicate Message-IDs and repeated shared CRM records appear once. Message bodies and attachments retain their source mailbox key; background refresh checks all authorized accounts, and new sent messages appear immediately in the company view. A read-only check on October 28, 2026 confirmed Gantri's contact was saved correctly and three received messages existed in the workspace cache; its empty company view came from loading only the default personal account.

The initial server response and `/api/email/inbox?companyId=...` refresh responses both filter messages to those contacts. The client also filters snapshots before updating the list. The company view has two columns: a conversation list with search, All/Unread filters, refresh and New email; and a reader with the same reply composer as the main mailbox. The composer opens expanded for company conversations, with AI writing enabled, AI reply, suggestions, attachments, catalogs, permitted invoice tools, emoji and calculator. AI draft previews and generation use the existing shared implementation. Narrow screens show the list or reader with a Conversations back button. Mailbox folders, bulk controls, automation, repeated account details, stars and category/source filters are omitted. Translation is optional and starts off. New conversations offer only the company's saved contact addresses. The tab uses the viewer's existing authorized mailboxes and saved-history limits; it does not import a separate company mailbox or send messages automatically.

## Mailbox structure review — October 22, 2026

The supplied OKKI reference has three states: a full-width mailbox overview; a selected message with a compact list, reader, and contact context; and an expanded inline reply. Persistent folder navigation, small date-grouped rows, unread emphasis, message actions, and independent scrolling make those states usable together.

The previous CRM opened the first conversation automatically, used large message cards and chat bubbles, hid folders and contact details below the widest breakpoint, duplicated Compose, and left the complete reply toolset permanently open. A second CRM navigation sidebar further reduced the reading area.

The email workspace now follows that structure:

- The initial view is a dense, date-grouped list with sender/address, subject, preview, time, unread state, reply/attachment indicators, stars, and selection. Opening a row switches to a compact list and document-style reader; Mailbox returns to the overview.
- Email is a standalone main navigation item, separate from Outreach, on desktop and mobile. It opens the mailbox directly without a secondary CRM submenu. Mail folders remain visible on desktop, with a folder selector on smaller screens.
- Inbox, Needs follow-up, Unread, All mail, Drafts, Scheduled, Sent, Starred, Archive, and Trash use existing message data and saved state. Needs follow-up uses the saved category. Sent uses outbound direction. Counts represent conversations in the loaded CRM snapshot, not provider-wide mailbox totals.
- Search, source/category filters, 30-conversation pagination, previous/next conversation navigation, and select-page controls work together. Bulk read/unread, archive/restore, and trash actions use `/api/email/state`; failed updates are reported without claiming success.
- Contact and follow-up details can be opened at every screen size. They appear alongside the reader on wide desktops and as an overlay on smaller screens. Quick reply expands on demand; collapsing it retains its content. Translation is available in the reader toolbar.

Provider spam/custom folders are not implemented: the persisted folder model currently supports Inbox, Archive, and Trash, independently of IMAP provider folders. Drafts and Scheduled show existing CRM records; the new-message composer does not yet save resumable drafts or schedule sends. AI guidance in the contact panel is general guidance, not a generated spam or buying-intent classification. These require separate backend work and should not be represented by cosmetic controls.

Verification used the authenticated local mailbox: saved inbox rendering, on-demand original HTML body loading, persisted read state, translation, reply expand/collapse, search, pagination, and bulk selection controls. Layout checks at 390 px and 1280 px found no document-level horizontal overflow; the normal wide desktop showed the list, reader, and contact panel together. No customer email was sent and bulk mutations were not exercised on customer messages. TypeScript, lint, tests, and production build are also checked before delivery.

The mailbox inbox used to download and parse 500 complete MIME messages on every 30-second refresh (1,000 for history). Attachments and provider login delays blocked every other message. It also silently excluded unknown senders. Saved CRM replies omitted RFC identifiers, so duplicate copies could appear as separate conversations. The reply composer selected the latest item's contact instead of the latest inbound message's Reply-To.

## Current flow

1. `/emails` and `/api/email/inbox` return saved messages immediately. The inbox route schedules provider refresh with Next.js `after`; the browser checks the saved result every 10 seconds while visible, and on focus.
2. The shared database lease permits one inbox sync per mailbox across server instances. `mailbox_sync_state` records UIDVALIDITY, the last acknowledged UID, errors, and up to 1,000 recent headers. A failed sync preserves the previous snapshot and cursor.
3. New mail sync imports at most 10 headers per batch, oldest first after the checkpoint. Initial sync takes the latest 10. Import history adds up to 25 older headers per click without rewinding the new-mail checkpoint. A UIDVALIDITY change discards the old epoch's header cache.
4. Opening a message calls `/api/email/message`. Only that message's plain-text and HTML MIME parts are downloaded, decoded with MailParser, and saved in `mailbox_message_content`. Older messages in a conversation have a Load message control. Attachments download separately through an authenticated route; inline image CIDs resolve through the same route, matching complete and URI-encoded IDs. The HTML viewer allows same-origin attachment cookies while keeping scripts, forms, and top-level navigation blocked. PNG/JPEG images and animated GIFs use the original attachment bytes.
5. Warm servers reuse authenticated IMAP sessions and serialize operations per session. IDLE mail/expunge notifications invalidate the checkpoint; unchanged checks can reuse it for up to 30 seconds. A periodic UID query still reconciles the provider. Connections expire after two idle minutes. Database snapshots remain authoritative across cold starts.
6. The existing minute cron also refreshes active mailbox caches when no live automation exists. Automation retrieves content only for new matching CRM replies; it does not store an empty header-only body.

## Conversation and sending rules

- Threading follows Message-ID, In-Reply-To, References, and saved CRM keys, including incomplete immediate-parent chains. Identical subjects alone do not combine inbound conversations. The restricted legacy outbound `Re:` fallback remains for older sent records.
- IMAP and CRM copies of the same received Message-ID are deduplicated. Saved CRM replies retain their message and thread identifiers.
- Reply uses the latest inbound Reply-To, or its From address. Sent-only conversations continue to the sent recipient. The composer displays the actual destination and keeps new-email composition separate.
- Reply headers retain original message-ID casing. Normal new messages have no reply headers. Plain text is not passed as HTML; explicitly supplied HTML remains a separate MIME alternative. SMTP connections have bounded timeouts and close after sending.
- Recognized quoted history is collapsed in the reader, with the original complete message available to expand.

Both cache tables have RLS enabled and deny direct anon/authenticated access. Server routes resolve the viewer's authorized effective mailbox and check its opaque mailbox key before serving content or attachments. Credentials are never stored in the cache or printed by the verification script.

## Verification and limits

AI reply is separate from AI writing. AI writing rewrites the manager's input in English, including the greeting, sign-off, and BD Sales Manager title, regardless of the CRM interface language or whether the input is Chinese, English, or mixed. Proper names and product identifiers are preserved. AI reply calls `/api/email/reply` to draft a response from the last eight original messages and the customer company profile, without requiring typed input. Header-only messages are loaded before generation. The existing Gemini provider and regional AI Gateway fallback must be configured and funded.

Catalog requests prepare a PDF using the latest saved company catalog selection, or the complete available product catalog. Explicit order requests return exact product/variant selections and quantities. The client then loads current billing context and prices through the existing invoice APIs, applies quantity tiers, validates MOQ and currency, saves a draft invoice, and downloads its draft PDF. Only roles already allowed to create invoices can perform this step. Unknown products, ambiguous variants, missing prices and mixed currencies require review. Shipping and tax amounts are not inferred.

The reply is installed only after all requested PDFs are ready. Users review the message and attachments and click Send email themselves. Generation never issues an invoice or sends an email. PDF retries reuse the saved draft for the same source customer message, and switching conversations prevents subsequent invoice writes and stale composer updates. The draft invoice review link opens the existing invoice editor.

## BD manager email visibility

For workspace mailboxes, the email page and inbox API restrict BD managers to saved contact addresses on companies currently assigned to them through `pipeline.owner_id`. This includes automatic and manual assignments and every contact on each company. Other managers' customers, unassigned customers, and unknown senders are excluded from every workspace inbox folder and its automation queue count. Matching uses exact email addresses, never company names or domains. Workspace message bodies and attachment downloads enforce the same assignment check. Assignment lookup errors deny workspace access; they do not fall back to the shared inbox. Personal mailbox owners can view every synced sender, message body, and attachment regardless of CRM assignments; other users cannot access that personal mailbox. Sent attachments resolve the message's stored mailbox ID rather than inferring ownership from the current default sender. Admin, operator, and viewer workspace access is unchanged.
