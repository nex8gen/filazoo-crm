# FILAZOO CRM agent

The CRM owns the agent's business knowledge, available actions, permissions and execution. A model interprets the request and calls those tools. Switching a qualified model does not require fine-tuning or rebuilding the agent.

In this CRM, **catalog is the previous name for quotation**. Both refer to Company Quotations. An invoice is a separate payment document. A quotation can start as a product selection, become a priced offer, record customer acceptance and create a draft order. It never silently becomes an invoice.

## What the agent can do

The versioned registry currently exposes 59 typed actions across customers, quotations, invoices, orders, products, email, tasks, workflows and settings. These include partial customer edits, private product prices, saved audience segments, quotation revisions/status, invoices/payment actions, order creation, email drafts and explicitly requested sending, conversation auto replies, follow-ups, prepared task actions, shipment updates, signature editing and administrator AI settings.

The complete feature inventory is [agent-capability-audit.json](./agent-capability-audit.json): server-action and mutating API exports classified as direct, guided, read helpers or internal infrastructure. The generated inventory contains the current counts as account and workspace features evolve. Multiple UI surfaces can share one agent tool, and one UI surface can expose several tools. Guided features remain UI handoffs, not completed agent actions. File uploads, passwords/OAuth/connection credentials, account/workspace ownership flows and specialized workflow test/composition controls use their existing forms.

Existing saved quotations can be attached by their real quotation ID. The server checks ownership and an approved fingerprint again when opening a draft or sending it. It renders the saved priced document or saved product selection, preserving agreed amounts instead of substituting today's whole product list.

Contract `2026-11-05.2` changes the default quotation scope: read the customer's actual email and include only requested products. An all-product selection requires an explicit user instruction. The server independently grounds new quotation selections and new quotation attachments, so changing models cannot restore the old blanket-catalogue default. It prefers exact saved product names/SKUs and unambiguous base materials, excludes unrelated specialty grades, and asks about missing or ambiguous names. Quoted old email text and outdated subjects cannot add products to a newer request. An explicitly selected existing quotation keeps its own saved content.

History/session recovery also returns JSON 503 on temporary workspace-verification failures, retries read-only session RPCs once, and gives the sidebar a retry control that preserves typed messages. Clients reconcile interrupted actions with saved results. A server-managed order workflow can continue from a durable checkpoint using the same order ID; uncertain SMTP delivery is never blindly replayed. An authenticated viewer's workspace is bound to that request so each data client does not repeat the same session lookup. Role checks and workspace isolation remain mandatory at request and action boundaries.

## Execution

The existing application uses Next.js route handlers and CRM services. Vercel AI SDK 7's `ToolLoopAgent` runs native tools exclusively through Vercel AI Gateway. Google and Anthropic model IDs are Gateway models, with shared Gateway authentication and billing. There is no direct Gemini API-key path or provider fallback. `@ai-sdk/google` supplies provider tool definitions for Gateway-backed Google Search and URL Context; it does not authenticate or send direct-provider requests.

1. Authenticate and load the authoritative saved conversation, selected record, accessible customer history and workspace policy.
2. Expose the relevant tool domains. The model can discover other domains and perform bounded, permission-scoped reads.
3. Validate tool arguments with the same Zod schemas used by the executable action layer. Native action tools also run read-only business preparation before staging: validation feedback returns to the model for correction without storing a proposal or executing a write. Portable JSON Schema presentation handles provider differences, such as empty-string enums; it never relaxes server validation.
4. Apply deterministic document-intent checks. Invoice/quotation substitution is rejected. A quotation email draft uses the existing attachment service rather than an unrelated document action.
5. Stage proposals in memory. The model loop performs no business mutations. Failed or mixed read/action batches are discarded. Compound order/invoice/email requests also undergo completion validation: an order-only or disconnected email proposal is discarded with feedback to the repair step.
6. Existing preparation, review, stored action claims, stale-record fingerprints and business services validate and execute the actions. Mandatory financial/destructive/admin reviews remain in force. A completion claim requires a saved execution result.

Local function schemas and arguments count as input/output tokens. Application usage limits and Gateway budget reservations have been removed. Each model step has bounded output, no hidden SDK retries, no provider conversation storage and no provider-side computer/code tool. Existing chat history and usage tracking continue to wrap the transport.

Reliability updates on 2026-11-07 increase the native planning window to 12 steps and allow two correction steps after an initial tool failure. New or edited purchase-order catalog lines are built from saved products before review, including variant identity, description, image and quantity-tier pricing. Manual prices and unchanged historical lines are preserved. The reviewed document participates in the execution fingerprint, so catalog changes require fresh review rather than applying a different amount.

An interrupted action response triggers bounded reads of the same saved action, never another mutation request. Completed results and partial-success links are restored; an unresolved running action has a Check saved result control. The owner-scoped endpoint returns only fields used by chat. Voice dictation retries transient network/silence interruptions at most twice, preserving accumulated text and canceling queued restarts when stopped. Permission and microphone problems provide neutral, actionable status messages. Genuine failures remain visible; they are never presented as completed work.

Contract `2026-11-07.1` adds a connected commerce workflow. `create_order` accepts saved customer/product/variant IDs and quantities, plus an optional requested email. `create_invoice` remains a compatibility entry into the same order-backed workflow. The server builds the commercial snapshot, allocates the order number, saves the order, obtains its automatically linked draft invoice and attaches that invoice's actual PDF. It does not require invented future IDs or an external PO number. Sending a draft invoice is distinct from drafting an email; explicit no-send instructions remain drafts.

The stored proposal ID is the new order's idempotency key and the email delivery operation's request ID. Checkpoints distinguish `order_starting`, `order_saved`, `invoice_ready`, `sending` and completion. A transient interruption before sending gets one automatic continuation under the original approval; unresolved pre-send work offers Resume remaining work. Resuming checks permissions and the reviewed invoice again. Changed commercial data requires fresh review. The real order-save service verifies the same owner/customer/document before reusing a creation ID, including a committed write whose response was lost. Once delivery enters `sending`, it cannot enter the automatic continuation path. Native runtime/version receipts are stored with replies and step logs include tool names without message bodies or credentials.

## Changing models or adding features

Gateway credentials are resolved inside each request by `lib/ai/provider-credentials.ts`. An explicit `AI_GATEWAY_API_KEY` takes precedence; otherwise the official `@vercel/oidc` helper reads Vercel's trusted runtime request context, with `VERCEL_OIDC_TOKEN` supporting local development and standalone workers. Enable OIDC in the linked Vercel project. Production does not require copying a local expiring token into environment settings. Agent, chat, email, research, workflows, tagging and inbox availability use the same resolver. Credentials are never cached across requests. Direct-provider credentials are ignored, even when the retired provider-selection or budget flags are present.

Model selection remains in `lib/ai/model-routing.ts` and environment settings. New model IDs must also have current pricing and reservation-policy support. Run the same synthetic qualification suite before enabling a new model. This is regression testing, not model training; arbitrary models are not assumed to have reliable tool support.

For a new CRM feature, add its typed action schema, business-service adapter, policy classification, label and domain description. The registry generates the model-facing contract from those executable schemas. Add relevant tests and update `scripts/audit-agent-capabilities.ts`, then regenerate the audit. The coverage test fails when a new server-action/API export has no inventory entry. Each guided feature must say where to continue and must not claim execution.

`AI_AGENT_RUNTIME=sdk` is the default for every Agent provider. `legacy` is an explicit rollback to the previous text-command loop. Normal Chat remains read-only. No production deployment is implied by this code change.
