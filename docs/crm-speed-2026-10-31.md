# CRM speed follow-up

Date: 2026-10-31 (UTC+8)

## Cause and runtime

The active local CRM was using `next dev` on port 3000. Development compiles routes on demand, does not automatically prefetch routes, and can invalidate open pages during code changes. The earlier session-memory work alone did not make this development runtime behave like the production app.

`npm run crm` now builds and starts an optimized local CRM at http://localhost:3001 with the existing local configuration. `npm run crm:start` restarts the prepared build without compiling. Its `.next-crm` output and generated TypeScript files are isolated from the normal `.next` development/build output. The launcher checks whether the port is occupied before building, preventing a second invocation from replacing a running CRM's assets. Stop this server before rebuilding it to apply code updates.

The optimized local runtime was started and left running for the user. Port 3000 and the user's existing development tab were left untouched. No remote deployment was performed.

## Changes

- Retained the earlier persistent settings layout, account-scoped view memory, and 30-minute visited-route cache. See [the navigation report](navigation-performance-2026-10-30.md) for retention and freshness boundaries.
- Removed the settings entrance animation that delayed the appearance of already loaded content.
- Company listings now retrieve only the newest email status per contact and omit unused embedded Meta lead payloads. Full company history remains available from its existing detail queries.
- Independent paid-order count batches run concurrently, with at most four batches in flight. Pagination within each batch remains sequential and complete.
- Production-shell bundle auditing supports the isolated runtime.

## Verification

The signed-in browser loaded Companies in the production runtime, visited Settings, waited at least ten seconds, and returned to Companies through primary navigation. The Companies heading was visible and CDP recorded no document or `_rsc` page-data request on that return. Settings return navigation also reused its loaded page payload. The final browser warning/error log was empty.

These are functional warm-navigation checks. They do not establish a reliable before/after latency benchmark or guarantee instant first visits. Full refreshes, explicit invalidations, cache eviction, and freshness updates can still require network work.

A read-only comparison across 229 companies found 139 embedded email-status rows before the query change and 51 afterward, with identical displayed outreach statuses. The paid-order reader also completed against the existing company IDs. No CRM records, settings, messages, or database schema were changed for these checks.
